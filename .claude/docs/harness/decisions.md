# 하네스 결정 기록

이 하네스의 질문과 결정. 실행 폴더의 `decisions.md` 와 같은 양식을 쓴다 (`.claude/docs/runs.md`).

## 쓰는 법

- `- [ ]` 미해결, `- [x]` 해결됨. **체크는 Claude 가 판단**한다 (사용자의 마지막 `->` 가 결정이고 남은 질문·모호함이 없으면 `[x]`).
- `  - ` 로 시작하는 줄은 **Claude** 발언 (배경, 권장, 답변). `  ->` 로 시작하는 줄은 **사용자** 발언 (답, 질문, 이의).
- 항목마다 끝의 빈 `  ->` 줄이 사용자가 적는 자리다. 서로의 줄은 고치지 않고 아래에 이어 쓴다.
- 확정된 항목에도 `  ->` 가 있다. 이의가 있으면 거기 적으면 Claude 가 `[ ]` 로 되돌리고 답한다.
- 앞으로 할 일은 여기가 아니라 `todo.md` 에 둔다.

## 미해결

(없음) 새 질문은 이 아래에 `- [ ]` 항목으로 추가한다.

## 해결됨 — 뼈대가 전제하는 결정

이 뼈대를 설치하면 아래 결정이 이미 들어 있다. 바꾸고 싶으면 이의를 적고 해당 파일을 고친다.

- [x] **하네스는 workplace 의 `.claude/` 에 두고, 작업은 항상 workplace 에서 시작해 대상 폴더를 지정한다.**
  - 사유: 여러 프로젝트를 가로지르는 개발 방법론이다. 도메인 지식은 하네스에 넣지 않는다.
  ->

- [x] **오케스트레이션은 `Agent` 도구(서브에이전트)만 쓰고 단계 사이는 파일로 전달한다. Task / Team 도구는 쓰지 않는다.**
  - 사유: 팀 도구는 실험 기능이라 모델·버전에 따라 가용성이 달라지고 비용도 크다. 파이프라인이 직렬이라 팀 대화가 필요 없다.
  ->

- [x] **산출물은 실행별 폴더** `knowledge/runs/{날짜}-{대상}-{슬러그}/` 에 두고 진행 상태는 `status.md` 에 기록한다.
  - 사유: 고정 번호 구조는 동시 실행이 불가능하고 재개·부분 재실행의 기준이 없다.
  ->

- [x] **프로젝트 지식은 `knowledge/docs/{그룹}/{대상}/` 에 둔다.** 하네스가 실행 중에 읽는 것은 여기, 하네스 설계 기록은 `.claude/docs/harness/` 에 둔다.
  ->

- [x] **저장소를 하네스 / 지식 / 프로젝트 셋으로 나눈다.** 하네스 저장소(환경 공통)는 `.claude/`, `CLAUDE.md`, `README.md`, `knowledge-template/` 만 추적(`.gitignore` 화이트리스트)하고, 프로젝트 문서·실행 기록·환경별 경계 사전은 `knowledge/`(환경별 별도 git)에 둔다.
  - 사유: 회사·집 여러 환경에서 하네스를 같이 갱신하면서, 회사 프로젝트 지식과 도메인 용어가 하네스(개인 원격)로 새지 않게 하고 지식 문서의 히스토리도 남기기 위해. 프로젝트 저장소 안에 두는 안은 회사 저장소에 `.claude` 를 올리지 않아 기각.
  ->

- [x] **지침과 강제를 구분한다.** CLAUDE.md 와 rules 는 지침이고, 경계는 점검 스크립트와 git hook 으로 강제한다. 멈춤·허용·차단은 settings(permissions, hooks)로 건다.
  ->

- [x] **개발 실행은 `knowledge/docs/` 를 자동으로 수정하지 않는다.** 문서에 반영할 후보는 `improvement-log.md` 에 남기고 반영은 사용자 승인 후에 한다.
  ->

- [x] **커밋은 규약(`rules/commit.md`)과 절차(`commit` 스킬)로 나눈다.**
