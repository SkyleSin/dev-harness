# 개발 하네스 청사진 (초안)

`harness-lab` Phase 0~7 순서의 초기 설계. 이후 변경은 이 문서가 아니라 실제 파일과 `changelog.md` 가 기준이다.
범용 규칙은 `lessons.md`, 결정은 `decisions.md`.

## Phase 0. 현재 상황

- 분류: 기존 확장 + 큰 아키텍처 변경 → Phase 1부터 다시 설계.
- 기존 하네스의 문제: ① 팀/Task 도구 의존 ② 프로젝트 도메인이 동작부에 섞임 ③ 산출물 단일 실행 ④ 이력 없음.
- 성숙도: 4단계(실패 처리·인수인계·기록 있음) → 목표 5단계(운영·개선 루프 정착).
- 이번 하네스의 두 가지 사용:
  1. **개발 실행**: 대상 폴더를 지정해 설계 → 구현 → 검증.
  2. **하네스 정비**: 규칙·에이전트·스킬 수정, drift 점검, 이력 기록.

## Phase 1. 사람의 작업 절차

1. 대상 폴더와 요청을 정한다.
2. 그 프로젝트의 지식(구조, 규약, 테스트 방법)을 읽는다.
3. 설계하고 모르는 것·결정할 것을 질문으로 모은다.
4. 사람이 설계를 승인한다.
5. 코드를 고친다.
6. 새 동작에 대한 테스트를 쓰고 돌린다.
7. 전체 테스트로 부수 효과를 확인한다.
8. 설계 대비 완결성·규약·품질을 검토한다.
9. 사람이 최종 승인한다.
10. 커밋 준비물(메시지 초안, 변경 요약)을 남긴다.

## Phase 2. 산출물 정의

### 하네스 7요소

| 요소 | 내용 |
| --- | --- |
| 목표 | 대상 폴더의 변경 요청을 검증된 코드 + 기록으로 만든다 |
| 컨텍스트 | 대상 프로젝트 지식 문서, 코드, 이전 실행 기록, baseline |
| 도구 | Read/Grep/Glob/Edit/Write/Bash, `Agent`. Task·Team 미사용 |
| 중간 산출물 | 입력 정리, 설계, 구현 요약, 테스트, 회귀, 리뷰 |
| 검증 | targeted 테스트, 전체 회귀(baseline 대조), 리뷰 체크리스트 |
| 권한과 승인 | Gate 1(설계), Gate 2(리뷰). 푸시·PR·배포는 하지 않음 |
| 기록과 개선 | `improvement-log.md`, `.claude/docs/harness/` 결정·교훈·변경 이력 |

### 설계 카드

| 항목 | 내용 |
| --- | --- |
| 반복 업무 | 프로젝트 기능 추가·변경·리팩터링 |
| 흔들리는 이유 | 컨텍스트 누락, 검증 생략, 규약 위반, 문서 drift |
| 최종 결과물 | 코드 변경, `final.md`(커밋 초안), 프로젝트 문서 갱신 후보 |
| 먼저 줄 자료 | 대상 프로젝트 지식 문서, 관련 코드, baseline |
| 먼저 물어볼 질문 | 대상 폴더, 회귀 모드, 결정이 필요한 설계 항목 |
| 중간 산출물 | `00-input` ~ `05-review` |
| 검증 기준 | 설계 항목 100% 반영, 테스트 통과, 신규 회귀 0, 규약 위반 0 |
| 실패 처리 | 유형 분류 → 대상 에이전트 재작업 1회 → 사용자 보고 |
| 사람 승인 | Gate 1, Gate 2, baseline 추가, 위험 상황의 회귀 skip |
| 다음 기록 | 개선 로그, 프로젝트 문서 갱신 후보 |

### 산출물 계약

실행 폴더 구조, 파일별 작성자·독자, `status.md`·`decisions.md` 양식, baseline 위치는 `.claude/docs/runs.md` 가 정본이다.

## Phase 3. 실행 모드와 패턴

- **모드: Subagent**, 순차 파이프라인 (작성 → 검토 패턴).
- 단일 흐름으로 충분하지 않은 이유: 구현자와 검증자의 컨텍스트를 분리해야 검증이 독립적이다.
- Team 을 쓰지 않는 이유: 직렬이라 팀원 간 대화가 필요 없고, 도구 가용성이 불안정하다 (`decisions.md`).
- 에이전트 호출 계약: 오케스트레이터가 프롬프트로 실행 폴더, 입력 파일, 출력 파일, 제약을 넘긴다. 에이전트는 **10줄 이내 결과 + 출력 경로 + 차단/질문** 만 돌려준다.
- 질문·승인은 서브에이전트가 못 하므로 **오케스트레이터가 중계**한다.
- 확장 자리(지금 만들지 않음): `work-ruler`(읽기 전용)를 T02 와 병렬로 백그라운드 호출. 기계 판정 규칙은 hook.

## Phase 4. 에이전트 (`work-` 접두)

각 에이전트의 입력·출력·하지 말 것은 `.claude/agents/work-*.md` 가 정본이다. 여기에는 분리한 이유만 남긴다.

| Agent | 분리 이유 |
| --- | --- |
| work-architect | 설계 책임 분리. 질문은 `decisions.md` 로 모은다 |
| work-implementer | 승인된 범위만 변경 |
| work-tester | 구현과 독립된 검증 |
| work-reviewer | 독립 판정. 코드를 고치지 않는다 |

## Phase 5. 스킬

스킬 목록과 역할은 `CLAUDE.md` 의 위치 표와 각 `.claude/skills/*/SKILL.md` 가 정본이다. 하네스 정비는 `harness-lab`, 대상 편입은 `project-onboarding` 이 맡는다.

**프로젝트 지식 계약**: 대상마다 `knowledge/docs/{대상}/overview.md`(구조·명령), 규약 문서, 테스트 방법이 있어야 하고, 그룹 공통 규약은 `knowledge/docs/{그룹}/common/` 에 둔다. 스킬은 이 문서를 **참조**만 하고 도메인 내용을 직접 담지 않는다.

## Phase 6. 오케스트레이터 흐름

진입 확인, 단계(T00-T06), Gate 1·2, 재작업 라우팅, 재실행 키워드는 `work-orchestrator` 스킬이 정본이다. 설계 원칙만 남긴다.

- 각 단계 전후에 오케스트레이터가 `status.md` 를 갱신하고, 다음 단계 전 이전 산출물 파일 존재를 확인한다.
- 하지 않는 일: push, PR, 배포. 위험 상황의 회귀 skip 은 사용자 확인 없이 확정하지 않는다.
- 자연어 라우팅은 `CLAUDE.md` 에 둔다.

## Phase 7. 테스트와 개선

테스트 프롬프트와 기대 동작은 `todo.md` 의 "가까운 일"이 정본이다.

- **정비 경로**: 하네스를 고치면 `.claude/docs/harness/changelog.md` 에 날짜·대상·사유를 남기고, `lessons.md` 와 `decisions.md` 를 갱신한다. 개선 요청은 청사진 → 승인 → 수정 순서.
- **이관 검증**: `lessons.md` 의 범용 항목이 스킬·에이전트에 모두 배치됐는지 대조한다.
