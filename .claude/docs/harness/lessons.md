# 하네스 교훈 목록

기존 하네스를 운영하며 추출한 범용 규칙. 새 개발 하네스 설계 시 체크리스트로 쓴다.
도메인 규약(프로젝트 규칙 문서로 갈 내용)과 환경별 기록은 이 문서에 두지 않는다.

## 범용 규칙

### 테스트 · 회귀

| # | 규칙 | 사유 |
| --- | --- | --- |
| 1 | baseline 파일 두 개를 섞지 않는다. `.txt`=알려진 실패, `.inventory.txt`=통과 목록. 실패 0건이면 빈 파일이 정상 | 통과 목록을 baseline 에 넣으면 delta 규칙이 뒤집혀 통과하던 테스트가 깨져도 "기존 실패"로 오분류됨 |
| 2 | 인벤토리 대조로 테스트 소실을 잡는다. 의도한 삭제인지 갱신 누락인지 구분해 기록 | 테스트가 조용히 사라져도 전체 pass 로 보임 |
| 3 | 신규 실패를 baseline 에 자동 추가하지 않는다 (사용자 승인) | 회귀를 "기존 실패"로 묻는 것 방지 |
| 4 | 실패한 테스트를 삭제·skip 해서 pass 로 만들지 않는다. targeted 실패 시 회귀 실행 안 함 | 결과 조작 방지 |
| 5 | 회귀 skip 이어도 산출물은 만든다. 위험 상황이면 경고를 숨기지 않고, 사용자 확인 없이 최종화하지 않는다 | skip 이 위험을 감추는 통로가 되는 것 방지 |
| 6 | 실행 결과는 실제 출력 기반, 사후 추측 금지 | |

### 코드 · 문서 품질

| # | 규칙 | 사유 |
| --- | --- | --- |
| 7 | docstring 은 현재 동작과 계약만. 이력·정정 배너·대안 검토·흐름도는 실행 산출물이나 프로젝트 문서로. 단 틀리면 조용히 깨지는 계약은 길이와 무관하게 유지 | 이력이 쌓여 안 읽히고, 안 읽히니 낡아도 모름 |
| 8 | 줄인 내용이 어딘가에 남았는지 확인한다. 코드에서 지우기만 하고 어디에도 안 남으면 fail | 줄이기가 정보 소실로 이어지는 것 방지 |
| 9 | 편집 중 발견한 장문 docstring 은 편집 대상 근처만 줄인다. 파일 전체 정리는 별도 요청 없이 안 한다 | 범위 이탈 방지 |
| 10 | 문서 정정은 누적 drift 를 한 번에 잡는다 | 부분 정정이 모순을 남김 |
| 11 | `improvement-log` 에 서비스 doc 갱신 후보를 남긴다 | 문서 drift 방지 |

### 질문 · 결정 (`decisions.md`)

| # | 규칙 | 사유 |
| --- | --- | --- |
| 15 | 질문과 설계를 분리한다. 질문은 대답할 수 있는 한 문장. Claude `-` / 사용자 `->`, 서로의 줄은 고치지 않고 이어 쓴다 | 설계 문서에 질문이 섞여 읽기 힘들고, 일일이 묻기 애매한 것을 모아 주고받으려고 |
| 16 | `[x]`=해결됨은 Claude 가 판단한다. 모호하면 `[ ]` 로 두고 이유를 적는다. 사용자가 이의를 적으면 되돌린다 | 사용자가 체크하면 "읽었다"인지 "해결"인지 불분명 |
| 17 | Claude 가 직접 확인할 수 있는 사실은 질문으로 올리지 않는다 | 불필요한 질문 방지 |
| 18 | 미확정 항목은 권장안을 가정하되 설계에 "미확정"으로 표시. Gate 1 에서 `[ ]` 목록을 먼저 알린다 | 모르는 걸 채우지 않으면서 진행은 막지 않기 |
| 19 | 정보가 없으면 추측으로 채우지 않는다 | 환각 방지 |
| 28 | 사용자에게 보내는 글은 결론 먼저, 완전한 문장, 내부 용어 풀이, 배경 → 선택지 → 권장안 → 결과 순서로 쓴다. 에이전트 반환문을 그대로 전달하지 않는다 | 압축된 반환문과 "한두 문장 보고" 지침이 채팅 설명을 함축하게 만들어 사용자가 판단하기 어려움 |
| 29 | 승인과 결정 요청은 채팅 프롬프트가 아니라 파일 항목으로 등록하고 채팅은 안내만 한다. 채팅 답도 받아 파일에 옮겨 적는다 | 채팅 질문은 흘러가 버려 앞 맥락을 다시 찾아야 하고, 기록이 파일에 남지 않음 |
