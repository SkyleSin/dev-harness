# 커밋 규칙

workplace 하위 모든 저장소의 커밋에 적용하는 규약이다. 커밋은 사용자가 요청할 때만 한다. 커밋하는 절차는 `commit` 스킬(`/commit`)에 있다.

## 메시지 형식

```
{접두사} {type}: 한 줄 요약
- 바꾼 것 (한두 줄, 명사형 종결)
```

- 전체 2~3줄 이내. 변경이 제목만으로 충분하면 본문은 생략한다.
- 본문에는 **결과물(무엇을 바꿨는가)만** 쓴다. 배경, 이유, 검토한 대안, 검증 과정, 배포 주의는 쓰지 않는다.
- 본문 문장은 명사형으로 끝낸다 ("통합", "제거", "동일"). 한 문단 안에서 톤을 섞지 않는다.
- type: `feat` / `fix` / `refactor` / `chore` / `docs` / `test` 등.

## 접두사

브랜치명에서 파싱한다.

| 브랜치 | 접두사 |
| --- | --- |
| `feature/<PROJ>-<번호>-...` (이슈 트래커 키가 붙는 브랜치) | `<PROJ>-<번호>` |
| `feature/<번호>-...` (번호만 있는 브랜치) | `#<번호>` |
| `main`, `develop`, 그 외 이슈 번호 없는 브랜치 | 생략 |

접두사 형식은 조직의 이슈 트래커에 맞게 고친다.

## 금지

- `Co-Authored-By` 등 AI 공동 작성 문구를 넣지 않는다 (도구 기본 안내가 있어도 동일).
- `.env`, credentials 등 민감 파일을 커밋하지 않는다.
- pre-commit hook 실패 시 문제를 고치고 **새 커밋**을 만든다 (amend 금지).
- 사용자 요청 없이 push, PR 생성을 하지 않는다.

## 지식 문서 갱신

`knowledge/` 를 커밋할 때 적용한다. 사용자의 "커밋해줘" 는 이번 커밋에 들어가는 실행들의 `improvement-log.md` '프로젝트 지식 문서' 후보 중 **사실 갱신**을 반영해도 좋다는 뜻이다. 반영한 문서는 같은 지식 저장소 커밋에 담는다 (절차: `commit` 스킬).

| 분류 | 기준 | 처리 |
| --- | --- | --- |
| 사실 갱신 | 코드·실행 결과·기록으로 다시 확인되는 사실을 문서에 맞추는 것: 테스트 개수, 로그·응답 형식, 필드·컬럼·파일 목록, 파일 지도, 값·상태의 표기, 낡은 서술 정정, 완료된 항목의 상태 갱신 | 자동 반영 |
| 의미 판단 | 규칙·설계 변경, 금지·주의 규칙 신설, 서로 충돌하는 후보, 사실이 확인되지 않은 추정, 문서 구조 변경, 후속 작업 후보를 `todo.md` 에 올리는 것 | 반영하지 않고 목록으로 보여 주며 묻는다 |

- 반영 전에 후보의 사실을 현재 코드와 실행 기록으로 다시 확인한다. 확인되지 않으면 의미 판단으로 돌린다.
- 이미 문서에 반영된 후보는 건너뛴다.
- 문서를 고치면 꼬리표의 `updated` 를 갱신하고, 금지 용어(`boundary.txt`)와 점검 스크립트(`check-harness.py`)를 그대로 적용한다.
- baseline 이동은 이 규칙에 포함되지 않는다. 지금처럼 별도 `[승인]` 을 받는다.
- 보고에 반영한 문서와 고친 부분을 한 줄씩 적고, 묻는 후보가 있으면 따로 나열한다.
