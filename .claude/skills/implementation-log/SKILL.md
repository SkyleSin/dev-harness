# implementation-log

## Overview

리뷰어와 테스터가 브리프 대비 무엇이 반영되었는지 빠르게 판단하게 한다. 브리프 항목마다 반영 여부를 표시하고 미반영 사유를 적는다.

## Workflow

1. `{RUN_DIR}/01-design.md` 의 변경 파일 목록과 각 섹션을 대조한다.
2. 실제로 편집한 파일 리스트를 얻고 (`git status` 등, `TARGET` 기준) 각 파일의 변경 요지를 한 줄로 요약한다.
3. 프로젝트 규칙 문서의 '명령'에 있는 lint/type 명령을 실행해 결과를 기록한다. 명령이 문서에 없으면 추측하지 않고 "확인 필요" 로 적는다.
4. 아래 양식으로 `{RUN_DIR}/02-implementation.md` 를 저장한다.

## 산출물 형식 (`02-implementation.md`)

```md
# 02. 구현 요약

## 변경한 파일
| 파일 | 유형 | 요지 |
| --- | --- | --- |

## 브리프 항목 체크리스트
| 브리프 섹션 | 반영 | 비고 |
| --- | --- | --- |
| 변경 파일 | ✅/❌ |  |
| 외부 시스템 · 데이터 영향 | ✅/❌ |  |
| 프로젝트 규칙 추가 섹션 | ✅/❌ |  |
| 테스트 계획 | (tester 담당) | |

## Lint / Type
- {lint 명령}: {pass/fail + 요약}
- {type 명령}: {pass/fail + 요약}

## 미완 또는 편차
- 

## 지식 문서 반영 후보
- (docstring 을 줄이며 문서에 남길 가치가 있는 것. 반영은 사용자 승인 후. 없으면 "없음")
```

## 품질 기준

- 브리프 항목 100% 반영. 부분 반영이면 미완/편차 섹션에 사유를 명시한다.
- lint/type 결과는 실제 명령 출력을 근거로 기록한다.
- 테스트 관련 편집은 하지 않았음이 분명하다 (변경 파일에 테스트 파일이 없다).

## 예외와 금지 행동

- 브리프 밖의 편집을 섞지 않는다. 있으면 별도 섹션에 명시하고 확인을 요청한다.
- lint/type 실패를 숨기지 않는다.
