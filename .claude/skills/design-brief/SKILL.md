# design-brief

## Overview

설계 브리프는 이후 구현·테스트·리뷰가 모두 근거로 삼는 문서다. 임의로 채우지 않고, 프로젝트 규칙 문서의 규약을 지킨 최소 완결 브리프를 만든다.

## Workflow

1. `project-context-loader` 반환값을 입력으로 확인한다.
2. 아래 양식의 각 섹션을 채운다. 프로젝트 규칙 문서의 '설계 브리프 추가 섹션'을 양식 끝에 이어 붙인다.
3. 프로젝트 규칙 문서의 규약에 위배가 없는지 자체 점검한다.
4. 사용자 결정이 필요하거나 정보가 부족한 부분은 `{RUN_DIR}/decisions.md` 에 항목으로 등록한다 (양식: `.claude/docs/runs.md`). 이미 있는 항목은 중복 등록하지 않고 `[x]` 항목은 확정으로 반영한다.
5. `{RUN_DIR}/01-design.md` 로 저장한다. 질문은 설계 문서에 쓰지 않고 항목 제목으로만 인용한다.
6. `01-design.md` 에서 뽑아 `{RUN_DIR}/design.md`(읽기용 요약)를 새로 쓴다. 아래 '읽기용 요약' 절을 따른다.

## 읽기 쉽게 쓰기

사용자가 읽는 문서(`design.md`, `decisions.md`)에 적용한다. `01-design.md` 는 뒷단계 에이전트가 읽는 정본이라 간결한 명세 형식으로 쓴다: 함축한 표현과 약어를 써도 되고, 쉬운 말 풀이·배경 설명·요약의 되풀이는 넣지 않는다. 표, 파일 경로, 근거(코드 위치)는 유지한다. 아래를 지킨다.

- **결론부터 쓴다.** 사용자가 승인에 쓰는 요약은 `design.md` 에 둔다(아래 '읽기용 요약'). `01-design.md` 는 뒷단계가 읽는 정본이라 요약을 되풀이하지 않고 맨 앞을 '단계별 읽기 범위'로 시작한다.
- **풀어서 쓴다.** 함축어, 약어, 화살표·기호 위주의 압축 표현을 피하고 주어와 서술어가 있는 문장으로 쓴다. 처음 나오는 약어와 내부 용어는 그 자리에서 한 문장으로 풀어 쓴다.
- **용어 풀이 절을 따로 만들지 않는다.** 필요한 설명은 본문에서 해당 말이 나오는 곳에 바로 쓴다.
- **형태는 구조화한다.** 순서가 있는 흐름은 번호 목록, 비교와 규칙은 표로 쓴다. 코드 경로와 같은 근거는 각 절 끝에 모은다.
- 대상 서비스 전체를 다루느라 길어지는 것은 허용하되, 세부(컬럼 목록, 단계별 테스트 케이스, 배포 노트)는 부록으로 내려 본문을 짧게 유지한다.

## 읽기용 요약 (`design.md`)

`01-design.md` 는 구현·테스트·리뷰가 근거로 삼는 정본이라 길어질 수 있다. 사용자가 읽고 승인하는 것은 번호 없는 `{RUN_DIR}/design.md` 다.

- `01-design.md` 를 다 쓴 뒤 그 내용에서 뽑아 새로 쓴다. `design.md` 에만 있는 정보는 두지 않는다. 설계가 바뀌면 `01-design.md` 를 먼저 고치고 `design.md` 를 다시 쓴다. 사용자 의견은 `decisions.md` 로 받고 `design.md` 를 직접 고치지 않는다.
- 80줄 안팎(점검 스크립트는 100줄을 넘으면 경고). 구성: 맨 위 기준 표시(`기준: 01-design.md, {날짜}`), 하는 일, 바뀌는 것, 승인받을 것, 지금 결정할 것(`decisions.md` 항목 제목, 없으면 "없음"), 구조 표 한 장, 상위 위험과 `확인 필요` 건수, 항목별 `01-design.md` 절 링크.
- 읽기 쉽게 쓰기 규칙(풀어서 쓰기, 용어 풀이 절 금지, 번호 목록·표)을 그대로 지킨다.

## 단계별 읽기 범위

여러 단계로 나뉜 변경(예: 이관 4단계)은 `01-design.md` 맨 앞에 표를 둔다: 단계, 읽을 절, 대상 파일. Orchestrator 가 뒷단계 에이전트를 부를 때 해당 단계의 절(공통 절 포함)만 읽도록 지정한다. 단계가 하나뿐이면 표를 생략한다.

## 산출물 형식 (`01-design.md`)

```md
# 01. 설계 브리프

## 단계별 읽기 범위 (여러 단계일 때만)
| 단계 | 읽을 절 | 대상 파일 |
| --- | --- | --- |

## 목표
- 요청 한 문장:
- 완료 기준:

## 대상
- {TARGET}

## 변경 파일
| 파일 | 변경 유형 (신규/편집/삭제) | 요지 |
| --- | --- | --- |

## 외부 시스템 · 데이터 영향 (해당 시)
- 호출 대상 / 변경되는 데이터:
- 실패·재시도 전략:

## 테스트 계획
- 커버할 케이스 (정상 / 경계 / 실패):
- 새 테스트 파일 경로 (제안):
- fixture 요구사항:

## 미확정 항목
- (decisions.md: 항목 제목) — 가정한 권장안 한 줄

## 프로젝트 규칙 추가 섹션
- {rules.md 의 '설계 브리프 추가 섹션' 을 그대로 옮겨 채운다}
```

## 품질 기준

- 프로젝트 규칙 문서의 규약 위배가 없다.
- 변경 파일 목록은 실제 존재하는 파일 또는 신규 파일 경로로 명확하다.
- `design.md` 가 80줄 안팎이고 `01-design.md` 와 어긋나는 내용이 없다.
- 테스트 계획에 정상 1개 이상 + 경계 또는 실패 1개 이상이 있다.
- 미확정 항목은 `decisions.md` 에 등록되어 있고, 설계에는 제목과 가정한 권장안만 적는다.

## 예외와 금지 행동

- 없는 파일 경로를 추측으로 넣지 않는다.
- 프로젝트 규칙 문서에 없는 규약을 새로 도입하지 않는다.
- 미확정 항목을 등록하지 않고 임의 결정으로 넘기지 않는다.
- `decisions.md` 의 사용자 줄(`  ->`)을 고치거나 지우지 않는다. 항목 제목은 대답할 수 있는 질문 한 문장으로 쓰고, 직접 확인할 수 있는 사실은 항목으로 올리지 않는다.
