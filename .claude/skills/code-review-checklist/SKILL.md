# code-review-checklist

## Overview

리뷰는 편향 없는 판단이 목표다. 스타일 취향이 아니라 근거(린트 규칙, 프로젝트 규약 조항, 브리프 문장)로 pass/fail 을 정한다.

## Workflow

1. `{RUN_DIR}/01-design.md`, `02-implementation.md`, `03-tests.md`, `04-regression.md` 를 모두 읽는다.
2. 변경된 코드와 테스트 파일을 직접 열어 근거를 확보한다.
3. 아래 체크리스트 각 항목에 pass/fail 과 근거를 적는다. 프로젝트 규칙 문서의 '리뷰 추가 점검 항목'을 같은 표에 이어 붙인다.
4. fail 항목의 대상을 실패 유형 표에 따라 지정한다.
5. `{RUN_DIR}/05-review.md` 에 저장한다.

## 산출물 형식 (`05-review.md`)

```md
# 05. Review

## 판정
- **pass** / **fail**
- 라우팅 대상: {없음 | implementer | tester | architect+사용자}

## 체크리스트
| 항목 | Pass/Fail | 근거 |
| --- | --- | --- |
| 브리프 완결성 |  | 01-design.md 의 각 섹션이 02/03 에 모두 반영 |
| Docstring 간결성 |  | 이력·정정 배너·대안 검토 없음, 모듈 5줄·함수 1줄 기준 |
| Lint / Type |  | 02 의 결과가 pass |
| Targeted 테스트 |  | 03 의 실행 결과 pass |
| 회귀 |  | 04 의 신규 실패 없음 / skip 이면 위험 경고 확인 |
| 테스트 소실 |  | 04 의 인벤토리 대조에서 의도하지 않은 소실 없음 |
| 테스트 커버리지 |  | 브리프 케이스 모두 커버 |
| (프로젝트 추가 점검 항목) |  | rules.md 에서 가져온 항목 |

## 실패 유형 판정 (fail 시)
| 유형 | 판단 근거 | 재작업 대상 |
| --- | --- | --- |
| 코드 이슈 | 브리프 스펙과 실제 동작 상충 | implementer |
| 테스트 이슈 | 브리프는 맞는데 assertion 이 잘못 | tester |
| 회귀 | baseline 대비 신규 실패, 변경과 인과 있음 | implementer |
| 브리프 애매 | 스펙이 두 가지로 해석 가능 | architect + 사용자 |

## 사용자 재확인 요청 (해당 시)
- {회귀 skip 위험 상황 등}

## 재작업 지시 (fail 시)
- 대상:
- 재작업 내용:
```

## 품질 기준

- 각 항목의 근거는 `파일:줄` 인용 또는 명령 출력 인용이다.
- fail 판정은 반드시 재작업 대상을 지정한다.
- 회귀 skip 이면서 tester 가 위험 경고를 남긴 경우 사용자 재확인을 요청한다.

### Docstring 간결성 판정

`work-implementer` 의 작성 규칙 위반을 잡는다. 아래가 보이면 fail (대상: implementer).

- 변경 이력 / 날짜 / "이전엔 X 였으나" / 정정 배너
- 설계 결정 배경, 버린 대안 설명
- 프레임워크 내부 동작 해설, 코드를 산문으로 옮긴 단계별 흐름도
- 모듈 docstring 이 한 줄 요약 + 5줄을 크게 넘김

**단, 계약 서술은 길이와 무관하게 유지한다.** 틀리면 조용히 깨지는 것(기대 상태, 반환값의 의미, 호출 순서 제약)은 짧게라도 남아 있어야 한다. 줄이라는 것이지 지우라는 게 아니다.

줄인 내용 중 지속될 가치가 있는 것이 `02-implementation.md` 의 '지식 문서 반영 후보' 에 남았는지 확인한다. 코드에서 지우기만 하고 어디에도 안 남으면 그것도 fail.

## 예외와 금지 행동

- 코드와 테스트를 직접 수정하지 않는다.
- 브리프에 없는 요건을 새로 요구하지 않는다.
- 스타일 취향으로 반려하지 않는다.
