# commit

## Overview

규약(무엇을 어떻게 쓰는가)은 `.claude/rules/commit.md` 에 있고, 이 스킬은 커밋하는 절차만 다룬다. 규약을 이 파일에 다시 적지 않는다.

## Workflow

1. 대상 저장소를 정한다. 커밋 대상은 최대 세 곳이다: ① 하네스(workplace 루트), ② `knowledge/`(프로젝트 문서·실행 산출물·baseline), ③ 실제 코드 저장소(`apps/…`, `tools/…` 등 하위 저장소). 세 곳을 모두 `git -C {저장소} status --short` 로 확인해 변경이 있는 저장소를 목록으로 보여 주고, 저장소마다 따로 커밋한다 (이력·원격·접두사가 저장소마다 다르므로 한 번에 묶지 않는다). 어느 저장소를 커밋할지 애매하면 묻는다. 이후 `git -C {저장소}` 로 실행한다.
2. 아래 명령을 병렬로 실행해 상태를 파악한다: `git status`, `git diff`(staged + unstaged), `git log --oneline -5`(최근 스타일), `git branch --show-current`.
3. 접두사를 그 저장소의 브랜치명에서 정한다 (표는 규약 문서). 저장소마다 브랜치가 다를 수 있다.
4. 규약에 맞춰 메시지를 쓴다. 사용자가 `$ARGUMENTS` 로 내용을 주면 반영한다.
5. 테스트: `pytest --collect-only -q` 로 수집되는 테스트가 있으면 `pytest` 를 실행한다. 실패하면 커밋을 보류하고 실패 내용을 보고한다 (사용자가 무시를 명시하면 진행). 테스트가 없으면 없이 진행할지 먼저 확인한다. 테스트 실행 방식은 통일안이 확정되면 갱신한다.
6. 지식 문서 갱신 (`knowledge/` 를 커밋할 때만, 기준은 규약 문서의 '지식 문서 갱신'): 이번 커밋에 들어가는 실행 폴더(`knowledge/runs/` 에서 아직 커밋되지 않은 것)의 `improvement-log.md` '프로젝트 지식 문서' 후보를 읽는다. 이미 반영된 후보는 건너뛰고, 나머지를 사실 갱신과 의미 판단으로 나눈다. 사실 갱신은 현재 코드와 실행 기록으로 다시 확인한 뒤 `knowledge/docs/` 에 반영하고 `updated` 를 갱신한다. 의미 판단 후보는 반영하지 않고 사용자에게 목록으로 묻는다. 반영 뒤 `python3 -I .claude/scripts/check-harness.py` 를 실행한다. baseline 이동은 하지 않는다 (별도 `[승인]`).
7. 관련 파일만 staging 하고 HEREDOC 으로 커밋한다. 6단계에서 반영한 문서는 같은 지식 저장소 커밋에 담는다.
8. 결과(커밋 해시, 파일 수)와, 6단계에서 반영한 문서·고친 부분을 한 줄씩, 묻는 후보가 있으면 따로 보고한다. push 는 하지 않는다.

## 예외

- pre-commit hook 이 실패하면 오류를 고치고 **새 커밋**을 만든다 (amend 금지).
- 민감 파일(`.env`, credentials 등)이 변경에 섞여 있으면 제외하고 알린다.
